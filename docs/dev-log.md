## 遇到的问题（按有趣程度排序）

### 1. 🎭 3D 翻牌卡的「无障碍树泄露」——本次最有价值的发现

做三选一翻牌时，卡的正反两面都真实存在于 DOM，只是用 `backface-visibility: hidden` 视觉隐藏。结果浏览器验收时发现：**翻牌之前，无障碍树（snapshot/屏幕阅读器）就能读出每张卡的稀有度和内容**——玩家看 DOM 就知道哪张是 SSR，直接摧毁抽卡游戏的核心体验。

修复：非当前面加 `inert` 属性（React 19 支持 boolean inert），把隐藏面从可访问性树移除，再给卡牌显式 `aria-label`（背面时只叫「第 N 张签」）。

> 通用结论：**任何"翻牌/刮刮乐/盲盒"类前端玩法都要检查这个**。`visibility/display` 方案会破坏 3D 动画，`inert` 是正解。

### 2. 🎰 SSR 3% 概率的视觉验收——比写游戏本身还费劲

要验收"抽中 SSR 的全屏特效"，就得真的抽中一次 SSR：

- 第一版循环脚本静默失败（`agent-browser find text` 匹配不到 aria-label 的卡牌按钮，点击无效果、报错被 `>/dev/null` 吞掉），**25 轮循环其实一直在读同一手牌**，一度误判为"概率系统有 bug"。
- 排查方法值得记录：直接在浏览器里 `import('/src/game/fortune.ts')` 统计 3000 手分布（N 49.6% / R 33.4% / SR 13.6% / SSR 3.5%，保底正常），证明逻辑无 bug、纯属运气 + 脚本空转。
- 最终方案：所有点击改用 `eval + querySelector` 直点，探针读卡面 textContent 定位 SSR，第 41 手左右命中。

> 通用结论：低概率路径的验收要么留 debug 后门（如 `?force=ssr`），要么接受自动化循环的不可控耗时。**下次先留后门。**

### 3. 📘 TS 5.5 类型谓词窄化陷阱

`if (hand.every(r => r === 'N'))` 在 TS 5.5+ 会被推断为类型谓词并把 `hand` 窄化成 `("N")[]`，导致后续 `hand[idx] = 升级结果` 类型报错。修复：显式注解谓词 `(r): r is Rarity => r === 'N'` + 用 `map` 替代原地赋值。

> 这种"新编译器行为 vs 旧知识"的冲突是 AI 写代码的典型坑，报错信息（`Type 'Rarity' is not assignable to type '"N"'`）一开始很有迷惑性。

### 4. ⚙️ 工具链版本漂移

- **Tailwind v4 没有 `tailwind.config.js`**：配置全走 CSS（`@theme` + `@import "tailwindcss"`），旧知识里的 config 文件方案无效。AI 需要按 v4 的 CSS-first 写法来。
- **tsconfig project references 需要 `composite: true`**：小项目直接单 tsconfig 更省事，删掉了 `tsconfig.node.json`。
- pnpm 10 默认不跑依赖的 postinstall 脚本（提示 `pnpm approve-builds`），对本项目无影响但值得知道。

### 5. 📝 测试侧的小坑

- 概率逻辑测试用**注入 rand 序列**做确定性断言（如 `[0.1, 0.2, 0.3, 0.99, 0.5]` → `['N','N','R']`），比统计断言精确得多；但必须**严格按实现里 rand 的消耗顺序**喂值——第一版把"选升级牌"和"掷升级目标"的顺序写反，测试失败但实现是对的。
- `Object.values()` 在泛型 `Record<T, number>` 上下文里返回 `unknown[]`，reduce 累加报错；改用 `Object.entries as [T, number][]` 一次转型两处使用。

### 6. 🥯 emoji 的 Windows 10 兼容性（上线首日用户反馈）

「手抓饼加蛋」用的 `🫓`（flatbread）是 Unicode 13.0（2020）新增，**Win10 的 Segoe UI Emoji 不含这个字形**，渲染成豆腐块；Win11 及 macOS/iOS/Android 均正常。用户在 Win10 上一眼看出。修复：换成 `🌯`（Unicode 8.0，2015 年起全平台支持），形态也贴合（手抓饼本就卷着吃）。对比截图：`docs/shots/08-emoji-probe.png`。

> 通用结论：**零素材方案选 emoji 时要按目标用户系统的 emoji 字体版本过滤**。Win10 的安全线大致在 Unicode 12（2019）以内；`🫓🥯🫒🧋` 等一批 2020+ 的"美食 emoji"恰好都是高风险区，对食物类游戏尤其致命。

## 出片效果评估

零外部素材（无图片/字体/音频），全部用 emoji + CSS/SVG + 系统字体：

- ✅ 首页：金色衬线大标题逐字入场、星光闪烁 + 樱花飘落背景，氛围达标
- ✅ 卡牌：夜蓝金边卡背带流光、稀有度渐变边框、SSR 彩虹流转边框
- ✅ 翻牌 3D 翻转 + 选中放大/未选压暗的对比编排
- ✅ SSR 全屏爆发（彩虹大字 + 三重扩散光环 + 星星粒子）有"值钱了"的感觉
- ✅ 运势结果卡信息完整、可一键导出 PNG（html-to-image，离线可用）
- ⚠️ 短板：emoji 作为"美术资产"上限明显——风格不可定制、跨平台渲染有差异；CSS 动画在低端机上的性能未验证

总体：**作为流程验证和轻度传播的小游够用，但要"美术风格化"必须引入矢量素材或生成式图片**。

## v2：升级为「游戏大全」（2026-09-04 同日）

把 A 重构成合集之一，并实现当初头脑风暴的 B/C/D 三个方案。新增的流程发现：

### 7. 🧭 架构上的两个决策

- **HashRouter 而非 BrowserRouter**：Pages 项目站挂在 `/game_demo/` 子路径且无法配服务端重写，hash 路由免配置、刷新不 404，深链如 `#/elimination` 可直接分享。
- **逻辑/展示分层约定**：每款游戏规则收敛到 `game.ts` 纯函数，`rand` 一律作为可注入参数——B 的轮盘步数、C 的平票规则、D 的并列随机因此都能写确定性单测（累计 30 个）。

### 8. 🎮 各游戏实现要点

- **B 极速淘汰赛**：4×4 网格内抖动散落避免重叠；「剩多个」时的轮盘决胜用 `steps % pool.length === 目标下标` 反推动画步数，保证高亮必然停在中选食物上（纯装饰动画与结果解耦）。
- **C 人格测试**：4 维度 × 每维度 2 题 = 16 人设；平票规则定为「第一题的答案决定」，保确定性。内容量是三款里最大的（8 题 + 16 人设文案）。
- **D 接食物**：rAF 循环里位置直接写 DOM style（`itemEls` Map 持引用），React 状态只存阶段数据（整秒倒计时/接住总数），避免 60fps re-render；掉落生成复用 A 的稀有度权重。键盘（window 事件）+ 指针（pointermove + `touch-none`）双输入，PC/手机一套代码。

### 9. 🤖 自动化验收脚本自身的坑（ again）

B 的验收里 `find text "不要XX"` 有几次静默失败（截图里 9px 的食物名看错字），C 的选项按钮因为文本是「A重油重辣…」前缀而非纯字母，`/^[AB]$/` 匹配不到。**UI 自动化的选择器永远优先用 data 属性/aria-label**——这已经是本仓库第二次栽在文本选择器上（第一次是 aria-label 卡牌）。
